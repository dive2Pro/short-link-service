# 从短链服务学习高可用与高并发架构

这份手册不把“高可用”理解成引入更多中间件。高可用是可量化目标、故障边界、降级策略、演练和恢复流程的组合。每次演进前先回答：流量是多少、允许丢什么、允许慢多久、故障时用户看到什么。

当前项目是一个单实例 Spring Boot + PostgreSQL 服务，适合作为演进起点，而不是高可用部署。下面的阶段按真实问题出现的顺序设计；每一阶段先完成实验和测试，再由你决定是否实现。

## 0. 先写目标，不先选组件

为每个接口分别定义 SLO。短链的读取和创建不能混为一谈：读取通常远多于创建，且跳转失败会直接影响用户访问。

| 场景 | 示例 SLO | 设计含义 |
| --- | --- | --- |
| `GET /{code}` 跳转 | 99.9% 成功率，p99 小于 100 ms | 优先缓存、快速失败、只读路径独立扩容 |
| `POST /api/links` 创建 | 99.9% 成功率，p99 小于 300 ms | 强一致写入、唯一性保证、明确冲突响应 |
| 数据恢复 | RPO 小于 5 分钟，RTO 小于 30 分钟 | 备份、演练、跨可用区副本 |

常用量纲：可用性 99.9% 每月约允许 43 分钟故障，99.99% 约 4 分钟。没有 RPO/RTO 的“多活”不是可验收的设计。

## 1. 并发正确性：从代码到数据库

目标契约可以命名为 `saveIfAbsent`，代表一个原子意图：“仅当 code 不存在时保存”。不要用“先 `findByCode`，再 `save`”保证唯一性；两个并发请求可能都在查询时看到不存在。

```text
请求 A: 查询 code=race -> 不存在
请求 B: 查询 code=race -> 不存在
请求 A: 插入成功
请求 B: 唯一约束冲突 -> 409 Conflict
```

练习时，内存实现可使用 `ConcurrentHashMap.putIfAbsent`；PostgreSQL 应使用唯一约束作为最终防线，并把约束冲突映射为 409。进程锁无法跨多个应用实例，因此不能取代数据库约束。

先为该契约写并发测试：

```bash
./mvnw test
```

让 64 个请求争抢同一个短码，预期恰好一个成功。随后把 `putIfAbsent` 暂时改为 `put`，观察为什么“线程安全容器”不等于“业务正确”。

当前项目的普通 `long sequence` 连单进程并发也无法保证正确性，这是并发练习的起点。改为 `AtomicLong` 后只能保证单进程内的自动生成不重复；进程重启、多实例部署和跨地域仍要求共享 ID 源，例如数据库序列号段、Redis `INCR` 号段或 Snowflake 类型 ID。转换为 Base62 后仍必须保留数据库唯一约束和冲突重试。不要把自增 ID 直接暴露给需要不可猜测链接的业务。

## 2. 读路径、缓存与一致性

短链读多写少，适合 cache-aside：先读 Redis，未命中再读数据库，成功后写缓存。创建、更新、禁用和过期时要删除或更新缓存。缓存不是数据库副本，它允许短暂陈旧，必须明确可接受的时间窗。

```text
Browser -> Load balancer -> Stateless app -> Redis cache -> PostgreSQL primary
                                      | miss              |
                                      +-------------------+
```

必须提前设计的现象：

- 缓存穿透：随机短码一直未命中。对空结果使用短 TTL 负缓存，或用 Bloom filter；不能无限缓存 404。
- 缓存击穿：热 key 过期后大量请求同时打到数据库。用 single-flight、短暂逻辑过期或互斥重建。
- 缓存雪崩：大量 key 同时失效。TTL 加抖动，预热热点，限制回源并发。
- 缓存故障：读路径应在有限并发和超时内回源数据库；数据库不足时返回明确 503，不能无限排队拖垮 JVM。

第一版练习：加入 Redis 前，用接口 `LinkLookupCache` 写一个 TTL 内存实现，并给出 hit、miss、fallback 三组测试。第二版把实现替换为 Redis，接口和业务层不变。

## 3. 限流、隔离与降级

限流保护的是依赖和用户体验，不是“防攻击开关”。至少区分 IP、用户/API key 和接口：读取可用较高配额，创建需要更低配额。

推荐顺序：网关做粗粒度限流，应用做业务配额，数据库连接池限制最终并发。令牌桶适合允许短暂突发；固定窗口实现简单但会有窗口边界突刺。

每个外部调用都必须有连接超时、响应超时、最大并发和重试预算。只对幂等请求重试；带指数退避和抖动；同一请求的总 deadline 不能被每层重试放大。

| 依赖状态 | 创建短链 | 跳转短链 |
| --- | --- | --- |
| Redis 不可用 | 直接写 PostgreSQL，记录缓存降级指标 | 有限回源 PostgreSQL |
| PostgreSQL 不可用 | 快速返回 503，不伪造成功 | 仅允许命中本地/Redis 的已缓存链接，否则 503 |
| 邮件/分析不可用 | 主流程成功，事件进入 outbox 后异步补偿 | 不影响跳转 |

熔断器不是第一步。先有正确的 timeout、并发隔离、指标和压测，再根据错误率与慢调用阈值配置熔断。错误地对数据库调用无限重试，比不重试更危险。

## 4. 数据、事务与异步化

短链映射的创建必须是同步且强一致的；访问计数、审计日志、风控和分析事件不应阻塞跳转。使用 transactional outbox：在同一个数据库事务写入映射和 outbox 事件，由独立消费者可靠发布到消息队列。

消费者必须幂等。消息系统通常至少一次投递，因此事件中放入不可变 event id，并在消费端记录已处理 ID 或让写入天然幂等。不要把“恰好一次”当作默认能力。

数据库演进规则：只用 Flyway 迁移；先扩展再收缩；新增字段先允许为空或给默认值；旧版本全部下线后再删除字段。生产中禁止 `ddl-auto=update`。

## 5. 可观测性与检测

完成 Actuator 练习后，服务可暴露：

```bash
curl http://localhost:8080/actuator/health
curl http://localhost:8080/actuator/health/liveness
curl http://localhost:8080/actuator/health/readiness
curl http://localhost:8080/actuator/metrics
```

生产环境不要把所有 Actuator 端点公开到互联网。经由内网、鉴权或管理端口访问。

监控至少覆盖四个信号：请求量、错误率、延迟分位数、资源饱和度。为短链再增加业务指标：创建成功/冲突数、缓存命中率、回源次数、跳转 404、限流拒绝数、消息积压。日志使用结构化 JSON，包含 request id、code、状态码和耗时，但不要记录完整敏感 URL 或凭据。

告警以用户影响为中心，例如“5 分钟跳转成功率低于 SLO”或“数据库连接池等待超过阈值”。CPU 高并不必然需要半夜叫醒人；没有用户影响的告警会迅速失去价值。

## 6. 测试金字塔与故障注入

| 层级 | 覆盖内容 | 例子 |
| --- | --- | --- |
| 单元测试 | 纯业务、时间、并发契约 | 固定 `Clock` 的短码创建测试 |
| Slice 测试 | MVC 校验、异常映射、JPA 查询 | `@WebMvcTest`、`@DataJpaTest` |
| 集成测试 | PostgreSQL/Flyway/唯一约束 | Testcontainers PostgreSQL |
| 契约测试 | 网关、调用方和响应兼容性 | OpenAPI 或 consumer contract |
| 压测/混沌 | 饱和、超时、节点和依赖故障 | k6、Gatling、Toxiproxy |

压测前先写工作负载：读写比、短码分布、URL 长度、并发连接、持续时间和正确性断言。只报 QPS 没有意义，必须同时记录 p50/p95/p99、非 2xx 比例、GC、连接池等待和数据库负载。

故障演练从可逆实验开始：停止一个应用实例、增加 Redis 延迟、拒绝 PostgreSQL 新连接、填满连接池。每次都要记录预期行为、实际指标、恢复步骤和改进项。

## 7. 高可用部署演进

```text
Phase 1: one app + one PostgreSQL
Phase 2: load balancer + >= 2 stateless apps + managed PostgreSQL backup
Phase 3: Redis + read replicas + outbox worker + dashboards
Phase 4: multi-AZ database, tested restore, regional failover runbook
Phase 5: multi-region only after latency, data ownership and conflict policy are explicit
```

应用实例必须无状态：会话、缓存、文件和定时任务不能依赖某一台机器本地磁盘。Kubernetes 的 readiness 失败时应摘流，liveness 失败时才重启；把数据库不可用直接作为 liveness 失败会导致所有实例同时重启，通常是错误的。

数据库 HA 不能只看主从复制。要验证备份是否可恢复、复制延迟是否满足 RPO、故障切换时连接如何重建、写入是否会短暂失败、迁移如何与滚动发布兼容。

## 8. 安全、成本与交付

短链常被滥用。需要 URL allow/block 策略、恶意域名扫描、创建配额、审计、举报与禁用能力。重定向时防止开放重定向规则被绕过；管理接口必须鉴权；数据库口令放入密钥管理而非 `application.properties`。

发布采用 CI 的编译、单元测试、迁移校验、镜像扫描和集成测试。部署采用滚动或金丝雀发布，先看错误率和延迟再扩容。每次迁移和发布都必须有回滚策略；数据库迁移通常只能向前修复，不能简单回滚 DDL。

## 建议的学习顺序

1. 完成本项目的并发测试，理解业务原子性。
2. 使用 Testcontainers 做 PostgreSQL 唯一约束集成测试。
3. 加入缓存接口和 TTL 实现，写击穿与降级测试。
4. 用 k6 写 90% 读、10% 写的压测脚本，建立基线。
5. 加入 Redis、限流和指标，再重复压测。
6. 实现 outbox 和幂等消费者。
7. 写一份 PostgreSQL 故障和恢复 runbook，并实际演练恢复。

每一步只引入一个新变量，并记录改动前后的 p99、错误率、资源占用和失败模式。这比一次性搭一套“云原生全家桶”更接近优秀工程实践。
