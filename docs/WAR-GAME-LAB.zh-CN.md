# 短链服务战争模拟实验册

这不是功能开发清单。每个实验都遵循同一闭环：先预测，再注入故障，再用指标观察，最后恢复与复盘。实验的目标不是让系统“永不报错”，而是在故障中保持可预期、可解释、可恢复。

只在本地 Docker 环境运行这些实验。不要在共享数据库、公司网络或生产环境执行破坏命令。

## 实验记录模板

每次实验先在 issue、Markdown 或笔记中填写下面模板，实验结束后补完“实际结果”和“改进”。没有记录的压测和故障演练很难沉淀为工程能力。

```text
实验名称：
日期与代码版本：
假设：
用户可感知的预期：
依赖与影响范围：

观测：p50/p95/p99、成功率、5xx、连接池、CPU、内存、数据库负载
停止条件：
注入步骤：
恢复步骤：
实际结果：
根因：
改进动作及验收：
```

## 统一安全规则

- 先确认目标容器和端口：`docker compose ps`。命令中的服务名必须与本项目 Compose 文件一致。
- 一次只注入一个变量。不要同时停 Redis、加延迟、启动压测，否则无法定位原因。
- 给压测设置并发、时长和停止条件；本地先从 10 到 30 秒开始。
- 数据库实验使用本地卷和测试数据。需要清空数据时，优先新建独立数据库，而不是清空正在使用的库。
- 每次中断后先恢复依赖，再确认健康检查和核心读写路径都恢复，才开始下一项实验。

## 实验 1：建立基线，而不是猜测容量

**问题**：没有基线时，无法证明新增缓存、限流或熔断究竟改善了什么。

**准备**：创建一批短链，其中包含少数热点短码。启动服务、PostgreSQL 和一个压测工具。k6 或 Gatling 均可，压测脚本至少包含：90% `GET /{code}`、10% `POST /api/links`、固定并发和持续时间。

**执行**：依次用 10、25、50、100 并发运行 30 秒。每次只提高一个档位。

**观测**：成功率、p50/p95/p99、应用 CPU/堆内存/GC、Hikari 连接池活跃与等待数、PostgreSQL CPU、慢查询、连接数和磁盘 IO。

**验收**：画出“并发数 -> p99/错误率”的曲线，标出第一个明显拐点。吞吐提升但 p99 急剧上升，不算容量提升。

**容量计算练习**：用 Little's Law 做第一版估算：`并发请求数 L = 到达率 lambda x 平均响应时间 W`。例如连接池 100、数据库平均一次查询 10 ms，理论上限约 `100 / 0.010 = 10,000` 次查询每秒。这不是承诺值，CPU、锁、SQL、网络和磁盘都会降低它；压测的职责是推翻或修正这个估算。

## 实验 2：并发写入与业务原子性

**问题**：`先查后写` 在多个请求同时到达时会产生竞态；进程内锁也无法覆盖多实例。

**注入**：让 64 个并发请求创建同一个自定义 code。

**预期**：一个创建成功，其他请求得到语义明确的 409；数据库中只有一行；没有 500，也没有重复记录。

**观测**：创建成功数、409 数、500 数、数据库唯一约束异常、表内该 code 的行数。

**验收**：先写失败测试，再实现原子 repository 契约与数据库唯一约束映射。把应用扩为两个实例并重复实验，验证结果不依赖单 JVM 锁。

**复盘问题**：自动短码的 ID 源在重启、扩容和跨地域时是否仍唯一？短码是否可被枚举？唯一约束为何仍不可省略？

## 实验 3：Redis 故障与降级

**前置**：先实现 cache-aside，并添加 Redis 容器。缓存与数据库都必须有显式连接/响应超时；先记录 Redis 正常时的基线。

**注入**：运行读流量后停止 Redis：

```bash
docker compose stop redis
```

**预期**：服务进程继续运行。读取请求在受控条件下回源 PostgreSQL；若数据库容量不足，尽快返回 503，而不是无限等待。创建短链不依赖缓存，仍可写入主库。

**观测**：Redis 错误数、缓存命中率、数据库 QPS、连接池等待、p99、503 比例。特别检查失败期间是否出现重试风暴。

**停止条件**：错误率持续超过设定 SLO，或连接池等待持续增长且 60 秒不能恢复，停止压测并执行恢复。

**恢复**：`docker compose start redis`；确认连接恢复、缓存逐渐回暖、数据库 QPS 回到基线附近。不要因为 Redis 恢复就宣布成功，必须检查服务是否曾被线程耗尽。

**扩展**：再模拟 Redis 慢而不是死。使用 Toxiproxy，或在仅限实验的容器网络中注入 500 ms 延迟。慢依赖更容易耗尽线程和连接池。

## 实验 4：缓存穿透、击穿与雪崩

| 场景 | 注入方式 | 预期防线 | 验收信号 |
| --- | --- | --- | --- |
| 穿透 | 高并发请求随机不存在 code | 短 TTL 负缓存或 Bloom filter | 数据库未随 404 请求线性飙升 |
| 击穿 | 热点 code 的缓存同时到期 | single-flight 或逻辑过期 | 只有少量回源请求 |
| 雪崩 | 批量 key 使用相同 TTL 后到期 | TTL 抖动、预热、回源并发上限 | p99 与数据库连接池不失控 |

不要一开始就使用分布式锁。先用指标证明存在击穿，再选择 single-flight、逻辑过期或锁，并验证锁本身故障、租约过期和重复计算时的行为。

## 实验 5：超时、重试、隔离和熔断

**目标**：区分第一次慢请求、有限重试和熔断后的快速失败。熔断器不是让第一次请求在 5 ms 内失败；它是在错误率或慢调用达到阈值后，暂时停止继续伤害依赖。

**前置设计**：定义请求总 deadline，例如跳转 200 ms。子调用的连接超时、读取超时、重试次数总和不能超过它。只重试幂等读请求，采用指数退避和抖动，并限制重试预算。

**注入**：让 Redis 或一个专门的下游 mock 固定延迟 1 秒，然后持续发送读取请求。

**预期**：

- 熔断阈值未达到前，少量请求在配置的超时后失败或走降级。
- 阈值达到后，后续请求快速走 fallback 或返回受控 503。
- half-open 只放少量探测请求；依赖恢复后闭合。
- 数据库连接池、应用工作线程和客户端连接数不持续增长。

**实现建议**：Java/Spring 项目可比较 Resilience4j 与 Sentinel；学习重点是状态机、阈值、指标和 fallback 语义，不是注解本身。先实现 timeout 和并发隔离，再加熔断；不能用无限重试替代熔断。

**验收**：记录熔断打开前后 p99、依赖调用数和应用可用线程数。证明快速失败确实减少下游压力，而不是仅仅把错误换成另一种错误。

## 实验 6：连接池耗尽与背压

**问题**：数据库慢时，应用请求会排队，随后工作线程、HTTP 连接和内存一起被拖垮。

**注入**：在测试数据库上用可控慢查询或代理延迟让查询耗时从基线提高到 500 ms，再运行固定并发读流量。不要在真实生产库上制造慢查询。

**预期**：连接池达到上限时，请求在有限等待后失败；服务保持响应；不会通过增加连接池无限压垮数据库。

**观测**：连接池 active/idle/pending、获取连接耗时、HTTP 线程池队列、GC、数据库连接数、p99 和 503。

**复盘问题**：连接池大小为何不能等于数据库最大连接数？应用实例扩为 10 个后，总连接数是多少？哪个位置应做并发上限与背压？

## 实验 7：网络丢包与部分失败

`tc netem` 可以模拟延迟、丢包和乱序，但它是 Linux 网络工具。在 macOS 上优先在一个 Linux Docker 容器或虚拟机中执行；给容器 `NET_ADMIN` 能力，只作用于实验网络命名空间。

示例思路，不要直接复制到未知容器：

```text
确认目标容器 -> 在目标容器内注入 100 ms 延迟和 10% 丢包
-> 运行固定读流量 -> 观察 timeout/retry/circuit breaker -> 删除 netem 规则
```

**验收**：请求失败率上升时，重试不会让下游 QPS 以倍数增长；服务返回的错误可区分超时、限流、依赖不可用和不存在短码。

## 实验 8：磁盘满、日志与资源水位

磁盘写满可以让日志、数据库 WAL、缓存持久化同时出问题。不要在宿主机或 Docker Desktop 的共享磁盘直接填满空间；在独立的大小受限卷或临时容器中实验。

**预期**：日志框架有滚动、保留和失败策略；业务线程不会因同步日志永久阻塞；磁盘使用率在达到危险水位前产生告警；数据库写入失败时不会向用户伪造成功。

**观测**：磁盘使用率、日志写入错误、应用线程状态、数据库 WAL/临时文件、创建接口的 5xx 与数据一致性。

## 实验 9：数据库故障、备份与恢复

**注入**：在本地环境停止 PostgreSQL，或拒绝新连接。不要把“重启数据库后服务又能连上”当成容灾验证。

**预期**：创建请求快速失败为 503；读取只允许返回已缓存的已知映射，否则 503；健康检查和告警能正确描述依赖状态；应用不因为数据库不可用反复重启。

**恢复演练**：

1. 创建可验证的数据集，记录条目数与校验值。
2. 执行备份，记录开始和结束时间。
3. 恢复到一个新数据库实例，不覆盖原库。
4. 执行 Flyway 校验，验证条目数、抽样内容和应用读写。
5. 计算实际 RPO 与 RTO，和第 0 章的目标比较。

**验收**：只有恢复过的备份才算备份。必须写出 failover、连接重建、数据校验和回切的 runbook。

## 实验 10：事故复盘训练

选一篇公开事故复盘，先只读“时间线”和“用户影响”，停止阅读方案部分。写下你对短链服务的预测：哪个依赖先饱和、会看到哪些指标、用户会收到什么响应、第一项止血措施是什么。再阅读原文，比较差异。

使用下面格式复盘你自己的实验，不追责个人：

```text
摘要：影响了什么用户功能，持续多久。
时间线：检测、确认、缓解、恢复分别发生在何时。
技术根因：触发条件与防线为何失效。
扩大因素：重试、排队、监控盲区、发布或操作错误。
处置：为什么当时的止血有效或无效。
行动项：负责人、截止日期、验收指标。
```

优秀复盘的输出不是“以后小心”，而是可验证的防线，例如“数据库连接等待超过 100 ms 告警”“读取总 deadline 为 200 ms”“恢复演练每季度一次”。

## 推荐顺序与毕业标准

按实验 1、2、3、5、6、9、10 的顺序推进。完成后再做缓存极端情况、网络与磁盘实验。

完成这套实验的最低标准是：你能为每个依赖故障说清楚用户看到什么、系统在哪里限流或降级、用什么指标发现问题、如何恢复、怎样证明下次不会以同样方式失控。组件名称不是答案，行为和证据才是答案。
